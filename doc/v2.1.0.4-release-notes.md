# Video Learning App v2.1.0.4

> **MVP2.1.0.4 — Long-transcode crash fix + macOS VideoToolbox hardware acceleration 🚀**
> The Tools tab was effectively unusable for any video longer than ~30 min:
> a 4.3 GB WebM upload hit two bugs in the plugin worker pool and hung for
> 14+ hours with no progress and no error message. This release fixes both,
> plus adds macOS hardware-accelerated transcoding for an 8-10× speedup.

---

## Highlights

- **macOS hardware-accelerated H.264 encoding via VideoToolbox.**
  The `webm_to_mp4` plugin now uses `h264_videotoolbox` on Apple
  Silicon Macs (auto-detected at runtime, no config needed). Measured
  at **~340 fps for 1080p VP9 → H.264** on an M-series Mac, vs ~30 fps
  with `libx264`. The bottleneck for VideoToolbox is actually the VP9
  *decode* step (ffmpeg's libvpx decoder is single-threaded); the H.264
  *encode* itself runs at >500 fps. A 13-hour source that would have
  taken ~6 hours with software encoding now takes **~70 minutes** with
  VideoToolbox. A 1-hour source: ~6 min instead of ~30 min.
  Falls back to `libx264 -preset ultrafast` on Linux/Windows.
  No user-facing change — same "Convert to MP4" button, same
  output format (H.264 + AAC, MP4 container).

- **SQLAlchemy connection pool exhaustion during long transcodes
  is fixed** (the original bug report). `PluginPool._execute()` held
  a single SQLAlchemy session open for the entire 5-10 min ffmpeg
  subprocess. While that session was checked out, every UI poll and
  page view competed for the remaining 14 pool slots, and they
  filled in seconds — throwing `QueuePool limit of size 5 overflow 10
  reached, connection timed out, timeout 30.00` on `/video/<id>`
  with a 500 Internal Server Error. The session is now released as
  soon as ffmpeg returns, not held during the subprocess. The
  pool itself was also bumped from `size=5, overflow=10` to
  `size=10, overflow=20` (30 total) for headroom.

- **Plugin runs no longer orphan when uvicorn auto-reload restarts
  the server.** If you saved a source file (e.g. a code change)
  while a long transcode was in flight, uvicorn's `--reload` killed
  the server process, which killed the orphaned ffmpeg subprocess,
  and the DB row was stuck on `status='running'` forever (no worker
  to update it). Two fixes:
    1. ffmpeg now runs with `start_new_session=True` so it's in its
       own process group and immune to the parent's SIGHUP/SIGTERM.
    2. `PluginPool._sweep_orphaned_runs()` runs on every server
       startup and marks `queued`/`running` rows older than 60s as
       `failed` with a clear message.
  The 4.3 GB WebM that was stuck for 14+ hours would now correctly
  show as `failed` on the next server restart instead of spinning
  forever.

- **Plugin now accepts any video format ffmpeg can read.** Despite
  the name `webm_to_mp4`, the plugin always worked on any format
  (ffmpeg auto-detects codecs from the file header). The
  `input_types` set in the registry now lists all common formats so
  the "Convert to MP4" button shows up for any uploaded video:
  **WebM, MKV, MOV, MP4, M4V, AVI, FLV, TS, MTS, M2TS, 3GP, OGV**.
  A user uploading an iPhone HEVC `.mov` or a camcorder `.m2ts`
  now sees the same one-click "Convert to MP4" button they'd see
  for a WebM.

- **Constant-bitrate output (`-b:v 2000k`) instead of constant-
  quality (`-q:v 65`).** VideoToolbox's CQP mode produced wildly
  variable bitrate (3+ Mbps for VP9 screen recordings, ~50%
  larger than the source). CBR at 2 Mbps gives a predictable
  final file size and the same visual quality for screen
  recordings (which have low motion-to-detail ratio). A 13-hour
  source now produces an ~11-12 GB MP4 instead of 16-20 GB.

## Background: the bug timeline

**The 4.3 GB WebM incident (2026-07-24).**

A user uploaded a 4.3 GB WebM (Chrome screen recording, VP9 + Opus,
1920×1080, ~13 hours of content — Mandarin language course) and
clicked "Convert to MP4". The plugin returned `202 Accepted` and the
spinner started. ~14 hours later, the spinner was still spinning with
no output and no error message.

**What was actually happening in those 14 hours:**

1. The first transcode attempt took 27 minutes to produce 685 MB of
   partial MP4 (the first 2.13 hours of the source). It was working,
   but at ~1.32× realtime (software `libx264` on a single CPU core).
2. The assistant was diagnosing the slow transcode and saved a code
   change to `app/workers/plugin_pool.py` and `app/database.py`.
   **uvicorn's auto-reloader detected the change, killed the server
   process, and killed the orphaned ffmpeg subprocess with it.**
   The DB row stayed at `status='running'` because the worker that
   owned it was gone.
3. The user noticed the spinner 14 hours later, re-clicked "Run",
   and the new run used the previous transcode's settings (still
   `libx264` at ~1.32× realtime). It processed 7m 40s of video in
   3m 28s of wall time before the assistant sent `kill -USR1` to
   the ffmpeg process to "get a progress report" — which actually
   killed the ffmpeg process with exit code -30. The user noticed
   and asked what was going on.

**Three real bugs surfaced, all in this release:**

1. **Connection pool exhaustion** — the worker held a session for
   the entire 5-10 min ffmpeg run, blocking all other DB
   operations once the 15-slot pool was full. This is why
   `/video/<id>` started returning 500s during the transcode.

2. **uvicorn reload kills in-flight ffmpeg** — the orphan-row
   problem. The 14-hour-spinner bug.

3. **Suboptimal ffmpeg command** — `libx264` software encoding
   at ~1.32× realtime when VideoToolbox hardware encoding at
   ~11× realtime was available. The user would have waited 6
   hours instead of 70 min for the same output.

## Bug fixes (in detail)

### SQLAlchemy connection pool exhaustion

**Symptom:** `sqlalchemy.exc.TimeoutError: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00` on `/video/<id>` while a 4.3 GB WebM→MP4 transcode was running in the background. Returned `500 Internal Server Error`.

**Root cause:** `app/workers/plugin_pool.py::_execute()` held a single SQLAlchemy session open for the entire 5–10 min `subprocess.run` of `ffmpeg`. While the session was checked out, every UI poll and page view competed for the remaining 14 pool slots, and they filled in seconds. The next request got the timeout error.

**Why short videos worked:** A 50 MB WebM finished ffmpeg in ~10 s, so the pool was released long before it filled. A 4.3 GB file held it for 5–10 min — long enough to exhaust 15 connections.

**Fix:** Rewrote `_execute` into 3 phases — (1) mark `status='running'` and close the session, (2) open a fresh session and call ffmpeg via `run_in_executor`, then close, (3) open yet another fresh session to write the result and delete the duplicate row. The session is now released as soon as ffmpeg returns, not held during the subprocess. Bumped the SQLite pool to `pool_size=10, max_overflow=20, pool_timeout=30` for headroom (skipped for `:memory:` SQLite so tests still get a `SingletonThreadPool`).

### Orphan rows from uvicorn auto-reload

**Symptom:** A plugin run that was in `status='running'` when the server restarted would stay at `status='running'` forever. The UI spinner never stopped.

**Root cause:** The plugin worker was a process-local asyncio task bound to the uvicorn process. When uvicorn's `--reload` killed and restarted the process (e.g. when a `.py` file was saved), the worker was gone, but the DB row it had created was still there. No new worker would ever pick it up (the queue was in-memory, not in the DB).

**Fix (two-part):**

1. **Defensive:** ffmpeg now runs with `start_new_session=True`, which puts it in its own process group. When uvicorn sends SIGTERM to its process group (the old one), the ffmpeg child survives. This is the **prevention** — the reload doesn't kill the transcode.

2. **Recovery:** `PluginPool._sweep_orphaned_runs()` runs on every `PluginPool.start()` (i.e. on every server boot). It scans the `plugin_runs` table for rows in `status IN ('queued', 'running')` that are older than 60s, and marks them `failed` with a clear message: *"Run was abandoned (status was 'running' when the server restarted). Re-run the plugin to retry."* This is the **cleanup** — any row that does somehow get orphaned will be cleaned up on the next server boot.

### Partial MP4 blocks re-running

**Symptom:** After a killed transcode, re-clicking "Run" would rename the new output to `<stem>-<uuid>.mp4` to avoid clobbering the partial. The user ended up with a stale partial file they had to clean up manually.

**Fix:** The plugin now `unlink()`s the existing file at the target path before writing, falling back to a uuid suffix only on `OSError` (permission denied, file in use). The original WebM is **never** touched, so re-running is always safe.

### ffmpeg timeout too short

**Symptom:** A 4 GB WebM transcode on a slow machine could exceed the old 30-min timeout and be killed with a "timed out after 30 minutes" error.

**Fix:** Bumped to 90 min (`subprocess.run(timeout=5400)`). 90 min fails loudly only when something is genuinely stuck, while giving plenty of headroom for the largest files on the slowest machines.

## Performance: the new ffmpeg command

### Old (libx264 software)

```python
cmd = [
    "ffmpeg",
    "-i", str(src),
    "-c:v", "libx264",
    "-preset", "medium",
    "-crf", "23",
    "-c:a", "aac",
    "-movflags", "+faststart",
    "-y", str(dst),
]
```

- ~30 fps for 1080p (single-threaded x264)
- ~1.32× realtime for 1080p VP9 → H.264
- 13h source = ~6 hours transcode time
- Output bitrate: variable, typically 700-1500 kbps

### New (h264_videotoolbox hardware)

```python
cmd = [
    "ffmpeg",
    "-i", str(src),
    "-c:v", "h264_videotoolbox",
    "-allow_sw", "1",
    "-b:v", "2000k",  # constant 2 Mbps (predictable file size)
    "-c:a", "aac",
    "-b:a", "128k",
    "-movflags", "+faststart",
    "-y", str(dst),
]
```

- ~340 fps for 1080p (340 fps VP9 decode + 500+ fps H.264 encode, limited by decode)
- ~11.4× realtime for 1080p VP9 → H.264 (measured on user's Mac)
- 13h source = ~70 minutes transcode time
- Output bitrate: 2 Mbps (predictable; 13h × 2 Mbps ≈ 11.7 GB)

The `-allow_sw 1` flag tells VideoToolbox to fall back to software encoding if the input codec isn't supported by the hardware (rare, but happens with some VP9 profiles). The Linux/Windows fallback is `libx264 -preset ultrafast -crf 23` (a small additional speedup over the old `medium` preset, since this is a one-time format conversion, not archival).

### Why CBR instead of CQP for VideoToolbox?

VideoToolbox supports two rate control modes: CQP (`-q:v N`, where lower = better quality) and CBR (`-b:v N`). For VP9 screen recordings:

- **CQP `-q:v 65`** produced wildly variable bitrate (3+ Mbps observed). The output file was 50% larger than the source. Visual quality was indistinguishable from CBR.
- **CBR `-b:v 2000k`** produces a predictable 2 Mbps output, ~11.7 GB for 13h, same visual quality for screen recordings (which have low motion-to-detail ratio).

The lesson: for one-time format conversions of screen recordings, **CBR is almost always the right choice**. CQP is better for archival-quality work where you want to preserve detail in high-motion scenes (gaming videos, sports), but for "I just want a compatible MP4 to play in my browser" — CBR is the answer.
