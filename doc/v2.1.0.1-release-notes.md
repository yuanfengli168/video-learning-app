## Highlights

- **Re-Upload button visible immediately after Run** — no more "I clicked Run, the transcode finished, but the button is missing until I refresh the page". The JS template now mirrors the server-rendered version.
- **No more page reload after Re-Upload with MP4** — swapping the video file updates the `<video>` element's `src` in place, with a cache-bust query param. The new MP4's duration + controls render in <100ms. No `Cmd+Shift+R` required, no bfcache stale state.
- **Closing the tab no longer kills your transcode** — plugin runs now go through a background worker pool (`asyncio.Queue` + `asyncio.Semaphore(3)`). The HTTP request returns 202 + `{run_id, status: "queued"}` in <50ms; the actual work happens in the server process and survives tab close.
- **Real-time status polling** — the UI polls `GET /api/plugins/runs/{id}` every 1.5s and shows `⏳ Queued...` / `⏳ Running...` / `✅ Done` / `❌ Failed` in the Run button. No more guessing whether the transcode is still going.
- **614 tests passing** (was 603, +11 new tests; 0 regressions; 1 pre-existing whisper-picker flake unrelated).

## What's in the box

### Tools tab UX fixes (2)

- **Re-Upload button now in JS template** — extracted as `renderSwapButton()` helper. Mirrors the server-rendered version, including the "disabled when video is not in `ready` state" condition. `videoStatus` is now exposed to JS so the helper can check.
- **No page reload after swap** — `performSwap()` sets `videoEl.src = /api/videos/.../file?v=${Date.now()}; videoEl.load();` instead of `setTimeout(location.reload, 800)`. Cache-bust query param forces a fresh fetch; `load()` re-reads metadata so the new MP4's duration + 3-dots menu render correctly.

### Plugin worker pool (backend)

- **New `app/workers/plugin_pool.py`** — `asyncio.Queue` + `asyncio.Semaphore(3)`. Bounded concurrency (3 parallel plugin runs); FIFO queue for the rest.
- **`PluginRun.status` field** — new `status` column on `plugin_runs` (additive migration; legacy rows backfilled to `'done'`). Values: `queued` / `running` / `done` / `failed`.
- **202 Accepted response** — `POST /api/plugins/{name}/run` now returns 202 + `{run_id, status: "queued"}` in <50ms. The previous sync code path blocked for 2-5 minutes for a typical 1-hour WebM transcode.
- **Polling endpoint** — `GET /api/plugins/runs/{id}` now includes the `status` field. UI polls every 1.5s.
- **Synchronous test mode** — `PluginPool.synchronous_mode = True` (set by the test `client` fixture) makes `submit()` run the plugin inline. Tests assert on the result without polling.

### Bug fixes

- **"Re-Upload with MP4" missing from JS-rendered last-run box** — the green success box rendered by `refreshLastRun()` only included "Open in Finder", not the swap button. Now both buttons are in both render paths.
- **"0:02" stale WebM state after swap** — `location.reload()` kept the bfcache'd page state, including the `<video>` element with `currentTime=0:02` from the old WebM. Now the swap updates `src` in place.

## Quick Start

Same as before — `bash scripts/start.sh` and open <http://localhost:8000>. No new env vars or setup steps.

For the new worker pool, the only config is the constructor argument in `app/workers/plugin_pool.py`:

````python
# In app/workers/plugin_pool.py
plugin_pool = PluginPool(limit=3)  # MVP2.1.0.1: limit=3
````

To change the limit, edit this line and restart the server. Future versions (2.1.1) will move this to a `settings` env var.

## Known limitations

- **Worker pool is in-process** — if the server crashes, queued + running plugin jobs are lost. The DB rows stay as `status='running'` (next startup can sweep them to `failed`). For MVP2.2 + multi-process, we'll move to Redis-backed queues.
- **Per-process singleton** — running uvicorn with multiple workers (`--workers 4`) would have 4 separate pools, each with its own queue. Fine for now (single-user MVP), but we'll need Redis when we add multi-user.
- **No cancellation** — once a plugin run starts, it can't be cancelled. ffmpeg doesn't have a clean signal-based cancellation, and we'd need a `threading.Event` + subprocess kill. Tracked for 2.1.0.2.
- **The `synchronous_mode` test escape hatch** — production code never sets this, but it's there in case tests need to bypass the worker. If you see `synchronous_mode = True` in production logs, that's a bug.
